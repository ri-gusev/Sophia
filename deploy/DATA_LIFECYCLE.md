# Резервное копирование, восстановление и удаление данных

Регламент рассчитан на аккаунтную SQLite сервиса «София». Ответственный за обработку и безопасность персональных данных — оператор Гусев Роман Игоревич. По его сведениям на VPS работает ежедневное копирование через SQLite Online Backup API, шифрование GPG AES-256 и автоматическое удаление локальных копий через 14 суток. Ключ хранится отдельно с ограниченным доступом. Расшифровка и целостность проверены. Для полного карантинного восстановления требуются отдельный прогон и протокол. Внешнее копирование допускается после подтверждения российского размещения и удаления всех копий и версий в пределах 14 суток с момента создания исходного снимка.

## Резервная копия

Используйте действующее задание с исправленной SQLite и GPG AES-256. Временный открытый снимок создавайте вне web root в закрытом каталоге режима 0700 с `umask 077`. Для временного открытого снимка используйте защищённый временный носитель, например подходящую изолированную область памяти или зашифрованный том. Исходная база и WAL хранятся на одном локальном томе. Выделите отдельное право на создание копий, а ключ хранения и восстановления держите под отдельным доступом. Проверяйте пропускную способность и блокировки операций backup на стенде. [SQLite Online Backup API](https://sqlite.org/backup.html)

Пример проверки части задания с SQLite внутри такого каталога. Запускайте с доступом к выбранной базе. Шифрование выполняется способом, настроенным и проверенным оператором в действующем задании GPG. Ключ и пароль не передаются в журнал, историю shell или аргументы команды.

```bash
set -euo pipefail
umask 077
test ! -e snapshot.sqlite
sqlite3 -bail /var/lib/sophia/accounts.sqlite '.timeout 250' '.backup snapshot.sqlite'
test "$(sqlite3 -bail -readonly snapshot.sqlite 'PRAGMA integrity_check;')" = ok
test -z "$(sqlite3 -bail -readonly snapshot.sqlite 'PRAGMA foreign_key_check;')"
```

Сверяйте код возврата каждого шага. Удаляйте временную открытую копию после создания шифротекста, а при сбое изолируйте рабочий каталог и удаляйте временные файлы по регламенту носителя. Подписывайте манифест с SHA-256, временем, SHA релиза и схемой или храните его с защищённой целостностью. До ручного внешнего переноса подтвердите место хранения, раздельные ACL, сроки, удаление и применимые ограничения. Проверяйте реплики, версии объектов, дисковые снимки и истечение TTL. Обычное удаление файла не гарантирует стирания блоков SSD.

Копируйте ledger отдельно, если он используется в закрытом окружении. Сверяйте операции после времени создания снимка с учётом провайдера. Для браузерных хранилищ, почты поддержки и Postbox учитывайте их собственные средства удаления и сроки.

## Восстановление в карантине

1. Отключите публичный трафик и остановите сервис. Сохраните повреждённую БД и WAL в ограниченном инцидентном хранилище при наличии основания. На новой изолированной площадке проверьте подпись или доверенную целостность манифеста и хеш шифротекста. С ограниченным доступом к ключу расшифруйте GPG в новый файл 0600. Сохраните исходную зашифрованную копию для отката. Текущую БД на этом этапе оставьте в карантине.
2. Сверьте идентификатор БД и версию схемы через CLI миграции на копии. Проверьте `integrity_check` со значением `ok` и отсутствие строк `foreign_key_check`. Подготовьте проверенный перечень остающихся аккаунтов из наиболее свежего доверенного источника и независимых записей об удалениях после снимка. Сверьте подтверждённый адрес и применимые ограничения каждого восстанавливаемого аккаунта. Не включайте спорные или удалённые аккаунты. При отсутствии достоверной сверки не открывайте восстановленную пользовательскую БД. Допустим запуск учебных страниц с изолированной пустой БД после отдельной проверки.
3. На приватном томе сформируйте файл `retained-accounts.txt` по одному проверенному уникальному ID на строку, без шапки, адресов и других данных. Откройте SQLite CLI на карантинном файле и выполните команды в **одном соединении**. Если нужно исключить все аккаунты, подготовьте пустой проверенный реестр.

```text
.bail on
CREATE TEMP TABLE retained_accounts(id TEXT PRIMARY KEY NOT NULL) STRICT;
.mode list
.import retained-accounts.txt retained_accounts
.read /srv/sophia/current/deploy/sql/prepare-account-restore.sql
PRAGMA integrity_check;
PRAGMA foreign_key_check;
```

4. Требуйте результат checkpoint `0|0|0`, целостность `ok` и отсутствие строк по внешним ключам. Сверьте число и состав восстановленных аккаунтов с реестром, ноль сессий, токенов, незавершённых заявок и entitlements. Пароли восстановленных аккаунтов отключены SQL-процедурой. Доступ возвращается через сброс на подтверждённую почту после проверки актуального получателя. Восстановленные согласия остаются историей снимка. До сверки более поздних отзывов и согласий не используйте восстановленную базу для рассылок. При отсутствии доказательств разрешать рассылку можно только после получения нового подтверждённого согласия по отдельно проверенному регламенту. Чат и регистрация остаются закрытыми.
5. Проверьте на отдельных синтетических данных, что удалённый аккаунт отсутствует, старая сессия, ссылка и пароль отклоняются, а запрошенное после восстановления письмо доходит и даёт установить пароль. Только после подтверждения состава записей и проверок подмените файл при остановленных процессах. Убедитесь, что старые WAL/SHM изолированы отдельно, каталог и файлы имеют корректных владельца и режим. Запустите закрытую приёмку. Храните протокол сверки и шифрованный журнал ошибок. Для возврата после неудачной попытки повторите процедуру карантина и проверки.

## Удаление и отзыв

- Из интерфейса пользователя отзыв обязательного согласия и удаление используют актуальный пароль. Транзакция удаляет аккаунт, сессии, ссылки восстановления, учебный прогресс, права и привязанные записи согласий. Отзыв рассылки фиксирует время и прекращает действие согласия. Он остаётся доступен при исчерпанном лимите повторных включений.
- При запросе оператору проверьте заявителя пропорционально риску, зарегистрируйте основание, сроки и объекты проверки. Не просите прислать пароль. Для ручного исполнения на закрытой площадке найдите подтверждённый внутренний ID через приватный интерфейс или параметризованный запрос и используйте команду с параметрами `DELETE FROM account_users WHERE id = ?` в транзакции с `foreign_keys=ON` и `secure_delete=ON`. Примените удаление связанных счётчиков по правилам `eraseAccount`, включая legacy и сетевые пары, а при обращении о незавершённой заявке — удаление её строк и ссылок. Панель администратора для этого workflow в приложении отсутствует.
- После commit проверьте отсутствие данных и активных токенов, выполните checkpoint TRUNCATE после освобождения читателей и подтвердите `integrity_check` и `foreign_key_check`. Отдельно разберите артефакты Postbox, поддержки, журналов, выгрузок и хранилищ. При открытии других устройств сервер не видит содержимого их локального хранилища. Сценарий в браузере очищает область аккаунта на текущем устройстве. Другие устройства обрабатываются отдельно.
- Запишите факт удаления в независимом закрытом реестре действий по восстановлению с минимальным идентификатором без контактных данных. Пока снимок может вернуть удалённую запись, исключите её из восстановления. При наличии применимого срока уничтожения удалите или выведите из использования затронутые копии и подтвердите удаление версий, реплик и снимков. Если действующие условия позволяют дождаться ротации заблокированной копии, отметьте основание, дату и итоговую проверку. Восстановление при расхождении с реестром запрещено.
- Самостоятельное удаление в профиле выполняет транзакцию в рабочей SQLite. В проверенном коде оно не пишет независимую запись с идентификатором удалённого аккаунта. Обезличенный HTTP-журнал не позволяет сопоставить удаление с записью из снимка. До допуска подтвердите источник независимой сверки и доказательств уничтожения для этого сценария опытным прогоном. Если после сбоя таких сведений нет, остановите восстановление затронутых аккаунтов.
- Стендовая приёмка включает удаление из актуальной базы, попытку восстановления из более раннего снимка в карантине, сверку независимого реестра, отзыв всех восстановленных полномочий и проверку ротации. Фиксируйте результат, проверяющего и подтверждение уничтожения по согласованному с оператором порядку.

## Применение регламента на Ubuntu VPS

Эти команды предназначены для выполнения оператором на сервере. Настройки `journald` затрагивают системный журнал VPS, включая журнал `sophia.service`. Сохраните минимально необходимые доказательства открытых инцидентов в закрытой области перед очисткой. Проверьте, куда дополнительно доставляются сообщения, включая `rsyslog` и внешние сборщики. Для потоков с данными сервиса обеспечьте тот же срок в каждом фактическом месте хранения.

```bash
set -o pipefail
sudo install -d -m 0755 /etc/systemd/journald.conf.d
printf '[Journal]\nMaxRetentionSec=14day\nMaxFileSec=1day\n' | sudo tee /etc/systemd/journald.conf.d/60-sophia-retention.conf >/dev/null
sudo systemctl restart systemd-journald
sudo journalctl --rotate
sudo journalctl --vacuum-time=14d
sudo systemd-analyze cat-config systemd/journald.conf | grep -E '^Max(Retention|File)Sec='
sudo journalctl -u sophia.service --until '14 days ago' --quiet -n 1 --no-pager -o cat | wc -l
```

В существующей секции `logrotate` для `/var/log/nginx/sophia.access.log` задайте `daily`, `rotate 13`, `maxage 14` и `ifempty` вместо `notifempty`. Это 13 архивов и текущий файл при ежедневной ротации, в том числе при отсутствии запросов. По шаблону этот файл обычно уже попадает под `/var/log/nginx/*.log`. Если на VPS есть другие сайты, выделите секцию для журнала «Софии», исключите пересечение путей и сохраните штатные `create`, `su` и `postrotate` с переоткрытием журналов Nginx. Проверьте секции и расписание. Соберите подтверждение содержимого и возраста архивов до публичного запуска, включая случай длительного простоя. [Ubuntu: journald.conf](https://manpages.ubuntu.com/manpages/noble/man5/journald.conf.5.html) · [Ubuntu: logrotate](https://manpages.ubuntu.com/manpages/noble/man8/logrotate.8.html)

```bash
sudo grep -nE '/var/log/nginx/|daily|rotate|maxage|ifempty|postrotate' /etc/logrotate.d/nginx
sudoedit /etc/logrotate.d/nginx
sudo nginx -t
sudo logrotate -d /etc/logrotate.conf
sudo systemctl enable --now logrotate.timer
systemctl list-timers --all logrotate.timer
sudo find /var/log/nginx -maxdepth 1 -type f -name 'sophia.access.log*' -mmin +20159 -printf '%f\n'
```

Команда `find` показывает файлы по времени изменения. При проверке архива сверяйте также метки событий, поскольку время изменения архива само по себе не гарантирует возраст его содержимого. Если `logrotate` делит настройки с другими сайтами, изолируйте секцию перед изменением их сроков.

Проверьте действующее задание резервирования и его ротацию без вывода содержимого скрипта, ключа или окружения. Если задание запускается не через systemd, сверяйте расписание в том планировщике, который настроен на VPS. Укажите фактический закрытый каталог и шаблон имён копий из проверенного задания. Следующий блок только считает просроченные файлы. Ожидается ноль после автоматического выполнения.

```bash
systemctl list-timers --all | grep -Ei 'backup|sophia'
read -r -p 'Абсолютный путь к закрытому каталогу копий: ' backup_dir
read -r -p 'Шаблон имён зашифрованных копий из задания: ' backup_glob
case "$backup_dir" in /*) ;; *) exit 1 ;; esac
test -n "$backup_glob" && test -d "$backup_dir" && test "$(realpath -- "$backup_dir")" != / &&
  sudo find "$backup_dir" -maxdepth 1 -type f -name "$backup_glob" -mmin +20159 -printf '.\n' | wc -l
```

До утверждения выпущенной версии проверьте снимки редакции 1.0. Запросы выполняются в режиме чтения и выводят только виды, версии и количество. Если в базе ещё нет таблиц, сначала сверяйте версию схемы по процедуре поставки. Публичные снимки 1.0 в рабочей базе требуют сверки с утверждаемыми текстами и датой перед допуском. Строка `age` исключена, поскольку текст отдельной отметки о возрасте сохранён.

```bash
sudo -u sophia-app sqlite3 -readonly /var/lib/sophia/accounts.sqlite <<'SQL'
SELECT kind, version FROM legal_revisions
WHERE version = '1.0' AND kind IN ('privacy', 'terms', 'consent');
SELECT 'registration_mailings', count(*) FROM account_mailing_consents WHERE version = '1.0';
SELECT 'profile_mailings', count(*) FROM account_mailing_revisions WHERE version = '1.0';
SQL
```
