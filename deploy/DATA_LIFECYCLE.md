# Резервное копирование, восстановление и удаление данных

Регламент рассчитан на аккаунтную SQLite сервиса «София». Ответственный за обработку и безопасность персональных данных — оператор Гусев Роман Игоревич. По его сведениям на VPS работает ежедневное копирование через SQLite Online Backup API, шифрование GPG AES-256 и автоматическое удаление локальных копий через 14 суток. Ключ хранится отдельно с ограниченным доступом. Расшифровка и целостность проверены. Для полного карантинного восстановления требуются отдельный прогон и протокол. Внешнее копирование допускается после подтверждения российского размещения и удаления всех копий и версий в пределах 14 суток с момента создания исходного снимка.

## Резервная копия

Используйте действующее задание с исправленной SQLite и GPG AES-256. Временный открытый снимок создавайте вне web root в закрытом каталоге режима 0700 с `umask 077`. Для временного открытого снимка используйте защищённый временный носитель, например подходящую изолированную область памяти или зашифрованный том. Исходная база и WAL хранятся на одном локальном томе. Выделите отдельное право на создание копий, а ключ хранения и восстановления держите под отдельным доступом. Проверяйте пропускную способность и блокировки операций backup на стенде. [SQLite Online Backup API](https://sqlite.org/backup.html)

Пример проверки части задания с SQLite внутри такого каталога. Запускайте с доступом к выбранной базе. Шифрование выполняется способом, настроенным и проверенным оператором в действующем задании GPG. Ключ и пароль не передаются в журнал, историю shell или аргументы команды.

```bash
set -euo pipefail
umask 077
test ! -e snapshot.sqlite
sqlite3 -bail /var/lib/sophia/accounts.sqlite '.timeout 250' '.backup snapshot.sqlite'
test "$(sqlite3 -bail -readonly snapshot.sqlite 'PRAGMA integrity_check;')" = ok
test -z "$(sqlite3 -bail -readonly snapshot.sqlite 'PRAGMA foreign_key_check;')"
```

Сверяйте код возврата каждого шага. Удаляйте временную открытую копию после создания шифротекста, а при сбое изолируйте рабочий каталог и удаляйте временные файлы по регламенту носителя. Подписывайте манифест с SHA-256, временем, SHA релиза и схемой или храните его с защищённой целостностью. До ручного внешнего переноса подтвердите место хранения, раздельные ACL, сроки, удаление и применимые ограничения. Проверяйте реплики, версии объектов, дисковые снимки и истечение TTL. Обычное удаление файла не гарантирует стирания блоков SSD.

Копируйте ledger отдельно, если он используется в закрытом окружении. Сверяйте операции после времени создания снимка с учётом провайдера. Для браузерных хранилищ, почты поддержки и Postbox учитывайте их собственные средства удаления и сроки.

## Развёртывание реестра удалений

Реестр — отдельная SQLite вне каталога основной базы. Запись содержит внутренний ID, время и основание: удаление из профиля, отзыв обязательного согласия или запрос оператору. Последовательность нужна для проверки непрерывности. Email, имя, пароль и прогресс в реестр не записываются. Главная транзакция фиксируется после устойчивой записи в реестре. При сбое записи основная транзакция откатывается. Если последующая фиксация SQLite не удалась, запись о намерении остаётся, а повторное удаление использует её же. Карантин исключает такой аккаунт до выяснения исхода.

В окно обслуживания закройте входящий трафик, остановите службу и разверните чистый артефакт. Убедитесь, что семь прежних URL портретов возвращают 404 через публичный прокси, включая возможный кэш. Используйте пользователя действующего сервиса.

```bash
set -euo pipefail
svc=sophia.service
app_user=$(systemctl show "$svc" -p User --value)
test -n "$app_user" && test "$app_user" != root
app_group=$(id -gn "$app_user")
sudo systemctl stop "$svc"
sudo install -d -m 0700 -o "$app_user" -g "$app_group" /var/lib/sophia-deletions
sudo systemctl edit "$svc"
sudoedit /etc/sophia/production.env
sudo systemctl daemon-reload
```

Для действующего unit в drop-in добавьте секцию `[Service]` с `StateDirectory=sophia-deletions` и `StateDirectoryMode=0700`. Новый шаблон unit уже объявляет оба каталога. В окружении задайте `ACCOUNT_DELETION_REGISTRY_PATH=/var/lib/sophia-deletions/registry.sqlite` и сохраните закрытые флаги. Следующая обёртка нужна также для команд ниже. Она обходится без чтения файла с секретами.

```bash
app_user=$(systemctl show sophia.service -p User --value)
accounts() {
  test -n "$app_user" && test "$app_user" != root || return 1
  sudo -u "$app_user" env NODE_ENV=production ACCOUNT_MODE=proxy \
    ACCOUNT_ORIGIN=https://sophialearn.ru \
    ACCOUNT_DB_PATH=/var/lib/sophia/accounts.sqlite \
    ACCOUNT_DELETION_REGISTRY_PATH=/var/lib/sophia-deletions/registry.sqlite \
    /opt/node-v24.22.3/bin/node /srv/sophia/current/scripts/accounts/cli.ts "$@"
}
accounts migrate
accounts init-deletions
accounts deletions-status
sudo stat -c '%a %U:%G %n' /var/lib/sophia-deletions /var/lib/sophia-deletions/registry.sqlite
```

Проверьте схему 8, владельца и режимы 0700/0600. Создайте новый снимок основной базы после привязки. Снимки до привязки не допускаются к восстановлению аккаунтов. При потере файла реестра нельзя создавать пустой взамен. Запустите службу в закрытом контуре командой `sudo systemctl start sophia.service`. Возврат к коду без учёта удалений допускается только при закрытых операциях аккаунтов. Миграцию нельзя отменять подменой рабочей базы на старый снимок.

## Резервирование и очистка реестра

В ежедневном закрытом задании выполняйте отдельный SQLite Online Backup реестра. Храните шифротекст отдельно от снимков аккаунтов в защищённом хранилище на территории РФ. Локальный срок реестра — 14 суток, по всему допустимому окну снимков. По мере очистки поднимается нижняя граница допустимых снимков. Копии реестра удаляются в пределах 14 суток с создания. Акт и доказательства уничтожения хранятся отдельно.

Пример для настроенного GPG с публичным ключом оператора и отдельным закрытым каталогом копий. Укажите полный проверенный отпечаток. Для ежедневного задания передавайте его как настроенный параметр вместо интерактивного ввода.

```bash
set -euo pipefail
umask 077
accounts prune-deletions
accounts deletions-status
read -r -p 'Полный проверенный отпечаток ключа GPG: ' fingerprint
[[ "$fingerprint" =~ ^([[:xdigit:]]{40}|[[:xdigit:]]{64})$ ]]
sudo install -d -m 0700 -o root -g root /var/backups/sophia-deletions
tmp=$(mktemp -d /dev/shm/sophia-erasure.XXXXXXXX)
trap 'rm -f -- "$tmp/registry.sqlite" "$tmp/registry.sqlite.gpg"; rmdir -- "$tmp"' EXIT
sudo sqlite3 -readonly /var/lib/sophia-deletions/registry.sqlite ".backup '$tmp/registry.sqlite'"
sudo chown "$(id -u):$(id -g)" "$tmp/registry.sqlite"
chmod 0600 "$tmp/registry.sqlite"
test "$(sqlite3 -readonly "$tmp/registry.sqlite" 'PRAGMA integrity_check;')" = ok
gpg --batch --recipient "$fingerprint" --cipher-algo AES256 --encrypt \
  --output "$tmp/registry.sqlite.gpg" "$tmp/registry.sqlite"
target="/var/backups/sophia-deletions/registry-$(date -u +%Y%m%dT%H%M%SZ).sqlite.gpg"
sudo install -m 0600 -- "$tmp/registry.sqlite.gpg" "$target.partial"
sudo mv -- "$target.partial" "$target"
sudo find /var/backups/sophia-deletions -maxdepth 1 -type f -name 'registry-*.sqlite.gpg' -mmin +20159 -delete
```

Сохраняйте подтверждённые ID реестра и последний номер события отдельно от файлов резервных копий в закрытом журнале эксплуатации. После остановки записи зафиксируйте последний номер действующего реестра. Старая копия подтверждает только события до момента её создания. При потере или подмене действующего реестра восстановление аккаунтов запрещено, пока его полнота до остановки записи не проверена независимым источником. Нельзя брать ожидаемый номер из самой проверяемой резервной копии.

## Восстановление в карантине

1. Отключите публичный трафик и остановите сервис. Сохраните повреждённую БД и WAL в ограниченном инцидентном хранилище при наличии основания. Проверьте доверенный манифест, хеш шифротекста и возраст снимка до 14 суток по отметке создания из манифеста. На изолированной площадке расшифруйте копию в новый файл 0600. Сохраните исходный шифротекст. Текущую БД на этом этапе оставьте в карантине.
2. На приватном томе подготовьте список действующих аккаунтов из наиболее свежего доверенного источника. Проверьте актуальность адресов и ограничений отдельно. Запишите один подтверждённый внутренний ID на строку в файл 0600 без заголовка. Проверьте ID и последний номер действующего реестра удалений по источнику, независимому от проверяемого снимка. Если достоверная сверка невозможна, оставьте восстановление закрытым. Учебные страницы можно запустить с изолированной пустой БД после отдельной проверки.
3. Запустите CLI с правом чтения реестра и работы только с карантинным файлом. Укажите ожидаемый номер из защищённого журнала эксплуатации. Команда проверяет привязку, непрерывность и границу истории, исключает зарегистрированные удаления даже при наличии ID в перечне и аннулирует все старые сессии, ссылки, пароли и права.

```bash
read -r -p 'Последний подтверждённый номер события: ' verified_sequence
accounts prepare-restore /var/lib/sophia/quarantine/accounts.sqlite \
  /var/lib/sophia/quarantine/retained-accounts.txt "$verified_sequence"
sudo -u "$app_user" sqlite3 -readonly /var/lib/sophia/quarantine/accounts.sqlite \
  'PRAGMA integrity_check; PRAGMA foreign_key_check; SELECT count(*) FROM account_sessions; SELECT count(*) FROM account_challenges;'
```

4. Требуйте успешного выхода CLI, целостность `ok`, отсутствие строк по внешним ключам и нулевые счётчики. Сверьте состав оставшихся аккаунтов. Доступ возвращается через сброс на подтверждённую почту после проверки актуального получателя. До сверки отзывов и повторных согласий записи снимка нельзя использовать для рассылок. Чат и регистрация остаются закрытыми.
5. Проверьте на отдельных синтетических данных, что удалённый аккаунт отсутствует, старая сессия, ссылка и пароль отклоняются, а запрошенное после восстановления письмо доходит и даёт установить пароль. Только после подтверждения состава записей и проверок подмените файл при остановленных процессах. Убедитесь, что старые WAL/SHM изолированы отдельно, каталог и файлы имеют корректных владельца и режим. Запустите закрытую приёмку. Храните протокол сверки и шифрованный журнал ошибок. Для возврата после неудачной попытки повторите процедуру карантина и проверки.

В отдельном checkout с зависимостями выполните синтетический сценарий. Команда создаёт временные SQLite и файловую почту.

## Удаление и отзыв

- Из интерфейса пользователя отзыв обязательного согласия и удаление используют актуальный пароль. Транзакция удаляет аккаунт, сессии, ссылки восстановления, учебный прогресс, права и привязанные записи согласий. Отзыв рассылки фиксирует время и прекращает действие согласия. Он остаётся доступен при исчерпанном лимите повторных включений.
- По запросу оператору проверьте заявителя соразмерно риску, зарегистрируйте основание и срок. Найдите подтверждённый внутренний ID в закрытом контуре. Передайте его команде через stdin без пароля и без журналирования терминального ввода. Сырой SQL-удалитель аккаунтов больше не используется. Для незавершённой заявки отдельно проверьте удаление её строк и ссылок.
- После commit проверьте отсутствие данных и активных токенов, выполните checkpoint TRUNCATE после освобождения читателей и подтвердите `integrity_check` и `foreign_key_check`. Отдельно разберите артефакты Postbox, поддержки, журналов, выгрузок и хранилищ. При открытии других устройств сервер не видит содержимого их локального хранилища. Сценарий в браузере очищает область аккаунта на текущем устройстве. Другие устройства обрабатываются отдельно.
- Сверьте отсутствие аккаунта в рабочей базе и соответствующую запись в реестре. Одиночная запись в реестре обозначает намерение, поэтому при наличии аккаунта в рабочей базе завершите удаление или расследуйте сбой до оформления акта. Экспортируйте необходимые строки реестра в закрытый акт и выгрузку событий. Дополните сведениями об уничтожении в почте и копиях и отметьте законное основание, если требуется блокировка до ротации.
- Стендовая приёмка включает удаление из актуальной базы, попытку восстановления из более раннего снимка в карантине, сверку независимого реестра, отзыв всех восстановленных полномочий и проверку ротации. Фиксируйте результат, проверяющего и подтверждение уничтожения по согласованному с оператором порядку.

```bash
read -r -s -p 'Проверенный внутренний ID аккаунта: ' account_id
printf '\n'
printf '%s\n' "$account_id" | accounts erase-account
unset account_id
```

## Применение регламента на Ubuntu VPS

Эти команды предназначены для выполнения оператором на сервере. Настройки `journald` затрагивают системный журнал VPS, включая журнал `sophia.service`. Сохраните минимально необходимые доказательства открытых инцидентов в закрытой области перед очисткой. Проверьте, куда дополнительно доставляются сообщения, включая `rsyslog` и внешние сборщики. Для потоков с данными сервиса обеспечьте тот же срок в каждом фактическом месте хранения.

```bash
set -o pipefail
sudo install -d -m 0755 /etc/systemd/journald.conf.d
printf '[Journal]\nMaxRetentionSec=14day\nMaxFileSec=1day\n' | sudo tee /etc/systemd/journald.conf.d/60-sophia-retention.conf >/dev/null
sudo systemctl restart systemd-journald
sudo journalctl --rotate
sudo journalctl --vacuum-time=14d
sudo systemd-analyze cat-config systemd/journald.conf | grep -E '^Max(Retention|File)Sec='
sudo journalctl -u sophia.service --until '14 days ago' --quiet -n 1 --no-pager -o cat | wc -l
```

В существующей секции `logrotate` для `/var/log/nginx/sophia.access.log` задайте `daily`, `rotate 13`, `maxage 14` и `ifempty` вместо `notifempty`. Это 13 архивов и текущий файл при ежедневной ротации, в том числе при отсутствии запросов. По шаблону этот файл обычно уже попадает под `/var/log/nginx/*.log`. Если на VPS есть другие сайты, выделите секцию для журнала «Софии», исключите пересечение путей и сохраните штатные `create`, `su` и `postrotate` с переоткрытием журналов Nginx. Проверьте секции и расписание. Соберите подтверждение содержимого и возраста архивов до публичного запуска, включая случай длительного простоя. [Ubuntu: journald.conf](https://manpages.ubuntu.com/manpages/noble/man5/journald.conf.5.html) · [Ubuntu: logrotate](https://manpages.ubuntu.com/manpages/noble/man8/logrotate.8.html)

```bash
sudo grep -nE '/var/log/nginx/|daily|rotate|maxage|ifempty|postrotate' /etc/logrotate.d/nginx
sudoedit /etc/logrotate.d/nginx
sudo nginx -t
sudo logrotate -d /etc/logrotate.conf
sudo systemctl enable --now logrotate.timer
systemctl list-timers --all logrotate.timer
sudo find /var/log/nginx -maxdepth 1 -type f -name 'sophia.access.log*' -mmin +20159 -printf '%f\n'
```

Команда `find` показывает файлы по времени изменения. При проверке архива сверяйте также метки событий, поскольку время изменения архива само по себе не гарантирует возраст его содержимого. Если `logrotate` делит настройки с другими сайтами, изолируйте секцию перед изменением их сроков.

Проверьте действующее задание резервирования и его ротацию без вывода содержимого скрипта, ключа или окружения. Если задание запускается не через systemd, сверяйте расписание в том планировщике, который настроен на VPS. Укажите фактический закрытый каталог и шаблон имён копий из проверенного задания. Следующий блок только считает просроченные файлы. Ожидается ноль после автоматического выполнения.

```bash
systemctl list-timers --all | grep -Ei 'backup|sophia'
read -r -p 'Абсолютный путь к закрытому каталогу копий: ' backup_dir
read -r -p 'Шаблон имён зашифрованных копий из задания: ' backup_glob
case "$backup_dir" in /*) ;; *) exit 1 ;; esac
test -n "$backup_glob" && test -d "$backup_dir" && test "$(realpath -- "$backup_dir")" != / &&
  sudo find "$backup_dir" -maxdepth 1 -type f -name "$backup_glob" -mmin +20159 -printf '.\n' | wc -l
```

До утверждения выпущенной версии проверьте снимки редакции 1.0. Запросы выполняются в режиме чтения и выводят только виды, версии и количество. Если в базе ещё нет таблиц, сначала сверяйте версию схемы по процедуре поставки. Публичные снимки 1.0 в рабочей базе требуют сверки с утверждаемыми текстами и датой перед допуском. Строка `age` исключена, поскольку текст отдельной отметки о возрасте сохранён.
