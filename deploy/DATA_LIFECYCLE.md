# Резервное копирование, восстановление и удаление данных

Регламент рассчитан на аккаунтную SQLite Sophia. Назначьте ответственного за операцию и проверяющего. Утвердите сроки, RPO/RTO, место размещения и круг доступа до сбора данных. Начальный эксплуатационный ориентир для копий — ежедневная копия и срок до 30 дней. Восстановление проверяйте перед запуском, после изменения схемы или инфраструктуры и затем по утверждённому расписанию.

## Резервная копия

Используйте SQLite Online Backup с исправленной SQLite. Записывайте временный снимок только в новый каталог режима 0700 на защищённом зашифрованном локальном томе. Исходная база и WAL хранятся на одном локальном томе. Выделите отдельное право на создание копий, приватный ключ восстановления храните отдельно от VPS. Проверяйте пропускную способность и блокировки операций backup на стенде. [SQLite Online Backup API](https://sqlite.org/backup.html)

Пример внутри такого каталога. Запускайте с доступом к выбранной базе, с `umask 077`. Файл получателей age должен быть подготовлен и проверен заранее.

```bash
set -euo pipefail
umask 077
test ! -e snapshot.sqlite && test ! -e snapshot.sqlite.age
sqlite3 -bail /var/lib/sophia/accounts.sqlite '.timeout 250' '.backup snapshot.sqlite'
test "$(sqlite3 -bail -readonly snapshot.sqlite 'PRAGMA integrity_check;')" = ok
test -z "$(sqlite3 -bail -readonly snapshot.sqlite 'PRAGMA foreign_key_check;')"
age -R /etc/sophia/backup-recipients.txt -o snapshot.sqlite.age snapshot.sqlite
sha256sum snapshot.sqlite.age > snapshot.sqlite.age.sha256
rm -- snapshot.sqlite
```

Сверяйте код возврата каждого шага. При сбое закрывайте рабочий каталог, удаляйте промежуточные файлы по регламенту зашифрованного тома и поднимайте оповещение. Не публикуйте открытый снимок, даже если проверка прошла. Подписывайте манифест с SHA-256, временем, SHA релиза и схемой или храните его в независимом хранилище с защищённой целостностью. Переносите шифротекст в утверждённое хранилище в РФ с раздельными ACL для записи, чтения, удаления и ключей. Проверяйте реплики, версии объектов, дисковые снимки и истечение TTL. Обычное удаление файла не гарантирует стирания блоков SSD.

Копируйте ledger отдельно, если он используется в закрытом окружении. Сверяйте операции после времени создания снимка с учётом провайдера. Для браузерных хранилищ, почты поддержки и Postbox учитывайте их собственные средства удаления и сроки.

## Восстановление в карантине

1. Отключите публичный трафик и остановите сервис. Сохраните повреждённую БД и WAL в ограниченном инцидентном хранилище при наличии основания. На новой изолированной площадке проверьте подпись или доверенную целостность манифеста и хеш шифротекста. Расшифруйте в новый файл 0600 под отдельным доступом. Сохраните исходную копию для отката процедуры, не подменяйте текущую БД этим файлом.
2. Сверьте идентификатор БД и версию схемы через CLI миграции на копии. Проверьте `integrity_check` со значением `ok` и отсутствие строк `foreign_key_check`. Подготовьте проверенный перечень остающихся аккаунтов из наиболее свежего доверенного источника и независимых записей об удалениях после снимка. Сверьте подтверждённый адрес и применимые ограничения каждого восстанавливаемого аккаунта. Не включайте спорные или удалённые аккаунты. При отсутствии достоверной сверки не открывайте восстановленную пользовательскую БД. Допустим запуск учебных страниц с изолированной пустой БД после отдельной проверки.
3. На приватном томе сформируйте файл `retained-accounts.txt` по одному проверенному уникальному ID на строку, без шапки, адресов и других данных. Откройте SQLite CLI на карантинном файле и выполните команды в **одном соединении**. Если нужно исключить все аккаунты, подготовьте пустой проверенный реестр.

```text
.bail on
CREATE TEMP TABLE retained_accounts(id TEXT PRIMARY KEY NOT NULL) STRICT;
.mode list
.import retained-accounts.txt retained_accounts
.read /srv/sophia/current/deploy/sql/prepare-account-restore.sql
PRAGMA integrity_check;
PRAGMA foreign_key_check;
```

4. Требуйте результат checkpoint `0|0|0`, целостность `ok` и отсутствие строк по внешним ключам. Сверьте число и состав восстановленных аккаунтов с реестром, ноль сессий, токенов, незавершённых заявок и entitlements. Пароли восстановленных аккаунтов отключены SQL-процедурой. Доступ возвращается через сброс на подтверждённую почту после проверки актуального получателя. Восстановленные согласия остаются историей снимка. До сверки более поздних отзывов и согласий не используйте восстановленную базу для рассылок. При отсутствии доказательств разрешать рассылку можно только после получения нового подтверждённого согласия по отдельно проверенному регламенту. Чат и регистрация остаются закрытыми.
5. Проверьте на отдельных синтетических данных, что удалённый аккаунт отсутствует, старая сессия, ссылка и пароль отклоняются, а запрошенное после восстановления письмо доходит и даёт установить пароль. Только после подтверждения состава записей и проверок подмените файл при остановленных процессах. Убедитесь, что старые WAL/SHM изолированы отдельно, каталог и файлы имеют корректных владельца и режим. Запустите закрытую приёмку. Храните протокол сверки и шифрованный журнал ошибок. Для возврата после неудачной попытки повторите процедуру карантина и проверки.

## Удаление и отзыв

- Из интерфейса пользователя отзыв обязательного согласия и удаление используют актуальный пароль. Транзакция удаляет аккаунт, сессии, ссылки восстановления, учебный прогресс, права и привязанные записи согласий. Отзыв рассылки фиксирует время и прекращает действие согласия. Он остаётся доступен при исчерпанном лимите повторных включений.
- При запросе оператору проверьте заявителя пропорционально риску, зарегистрируйте основание, сроки и объекты проверки. Не просите прислать пароль. Для ручного исполнения на закрытой площадке найдите подтверждённый внутренний ID через приватный интерфейс или параметризованный запрос и используйте команду с параметрами `DELETE FROM account_users WHERE id = ?` в транзакции с `foreign_keys=ON` и `secure_delete=ON`. Примените удаление связанных счётчиков по правилам `eraseAccount`, включая legacy и сетевые пары, а при обращении о незавершённой заявке — удаление её строк и ссылок. Панель администратора для этого workflow в приложении отсутствует.
- После commit проверьте отсутствие данных и активных токенов, выполните checkpoint TRUNCATE после освобождения читателей и подтвердите `integrity_check` и `foreign_key_check`. Отдельно разберите артефакты Postbox, поддержки, журналов, выгрузок и хранилищ. При открытии других устройств сервер не видит содержимого их локального хранилища. Сценарий в браузере очищает область аккаунта на текущем устройстве. Другие устройства обрабатываются отдельно.
- Запишите факт удаления в независимом закрытом реестре действий по восстановлению с минимальным идентификатором без контактных данных. Пока снимок может вернуть удалённую запись, исключите её из восстановления. При наличии применимого срока уничтожения удалите или выведите из использования затронутые копии и подтвердите удаление версий, реплик и снимков. Если действующие условия позволяют дождаться ротации заблокированной копии, отметьте основание, дату и итоговую проверку. Восстановление при расхождении с реестром запрещено.
- Стендовая приёмка включает удаление из актуальной базы, попытку восстановления из более раннего снимка в карантине, сверку независимого реестра, отзыв всех восстановленных полномочий и проверку ротации. Фиксируйте результат, проверяющего и подтверждение уничтожения по согласованному с оператором порядку.
