# Аудит производительности Sophia перед MVP

Проверяемая версия приложения — `b71b1ad`. Публичный ИИ-чат выключен. Целевая среда — Ubuntu 24.04 LTS, `ru-central1-b`, Nginx, Node.js 24 и systemd, один экземпляр приложения, без Docker.

## Предварительный выбор VPS

| Профиль | vCPU 100% | RAM | `network-ssd` | Назначение |
|---|---:|---:|---:|---|
| Минимальный кандидат | 2 | 2 ГиБ | 20 ГиБ | Закрытый стенд с внешней сборкой и коротким удержанием логов |
| Рекомендуемый старт | 2 | 4 ГиБ | 30–40 ГиБ | MVP с внешней сборкой, ротацией логов и внешней резервной копией |
| Запас | 4 | 8 ГиБ | 40–50 ГиБ | Если Ubuntu-прогон покажет исчерпание CPU/RAM или потребуется сборка на хосте |

**4 ГиБ RAM и 2 vCPU — стартовая оценка для рантайма.** Проверка на целевой машине определит рабочую ёмкость. **40 ГиБ достаточно по дисковому бюджету** для текущих ресурсов и резерва эксплуатации. При гранте 4000 ₽ разумно начать с 30 ГиБ, если резервные копии хранятся вне ВМ и нужны только текущий и предыдущий релизы. 2 ГиБ swap дают аварийный запас. Устойчивый swap-in во время запросов — сигнал снижать нагрузку или увеличивать RAM.

## Архитектура и точки нагрузки

| Поверхность | Сервер | Браузер |
|---|---|---|
| `/` | Динамический HTML/RSC и состояние аккаунта через корневой layout | Вопрос дня, проверка выбора, анимация и серия через `localStorage` |
| `/learn` | Динамический HTML/RSC оболочки, авторизованные GET/POST `/api/progress` | Карта курса, шаги урока из URL-фрагмента, упражнения, анимации и гостевой прогресс |
| `/atlas` | Динамический HTML/RSC оболочки, раздача чанков, текстур и портретов | Three.js/WebGL через динамический импорт с `ssr: false`, временная шкала, карточки и вращение |
| `/profile` | Сессия, чтение SQLite и подготовка данных учебного профиля | Календарь на 365 дней, раскрытие направлений и настройки |
| `/login`, `/register`, восстановление и юридические страницы | HTML/RSC, API аккаунта, сессии, лимиты, доставка почты | Формы и локальная интерактивность |

Сборка Next.js 16.4.6 маркирует все страницы и API как `ƒ`, а `/icon.svg` — `○`. Корневой layout вызывает `currentAccount()`, который использует `cookies()`. Гость без cookie завершает поиск сессии до обращения к SQLite. React `cache()` позволяет профилю и layout разделить один lookup в рамках рендера. Статические изображения и чанки раздаются отдельно. Отдельного маршрута читалки в `src/app` нет.

При старте Next загружает серверный рантайм, манифесты и нужные модули. Пул процессов TypeScript и воркеры генерации страниц составляют отдельную нагрузку сборки. Память Node растёт после первых SSR/API-запросов, когда загрузятся чанки, сериализуются ответы и откроется SQLite. В режиме `proxy` стартовый хук дополнительно запускает очистку просроченных аккаунтных записей и WAL checkpoint с последующим повтором по таймеру. Замер локального режима с файловой почтой эту работу и SMTP-задержку не включает. Глобус, текстуры и визуальные эффекты расходуют память браузера и GPU. Размер файла статического ресурса сам по себе не измеряет его расход RAM в браузере.

SQLite использует синхронный `DatabaseSync`, WAL и `BEGIN IMMEDIATE` для изменений. WAL позволяет чтениям идти параллельно с записью, но одновременно работает один writer. У аккаунтной базы задано ожидание блокировки 250 мс. В одном процессе даже ожидание блокировки задерживает общий цикл событий. Прогресс выполняет транзакционную запись и перечитывает снимок с ревизией перед ответом. При росте базы следить за длительностью транзакций, WAL, размером очереди записей и 503. PostgreSQL имеет смысл при устойчивых конфликтах записи или необходимости нескольких экземпляров приложения с общей БД. Число зарегистрированных пользователей само по себе миграцию не определяет.

Вход и подтверждение регистрации используют асинхронный Argon2id через `node:crypto` с 65 536 КиБ, тремя проходами и параллелизмом 1. Первичная заявка регистрации выполняет SQLite и запись письма, а хеширование происходит при активации. На Node-процесс одновременно допускаются два хеша, до 128 МиБ рабочей памяти плюс накладные расходы. Остальные получают 429 с `Retry-After: 2`. При входе лимит локальной сети составляет 35 запросов за 15 минут, глобальный — 300, на email — 6. Сетевое окно расходуется до проверки свободного слота хеширования. При регистрации лимит на сеть составляет 12 в час, глобальный — 60 в час. При одиночном источнике интенсивный вход показывает первый всплеск хеширования и затем реакцию лимитера.

Обработчик ИИ-чата проверяет флаг до проверки доступа, авторизации, аренды бюджета и выполнения запроса. RAG извлекается в пути ответа, его SQLite-хранилище и провайдер при закрытом чате не используются. Модули маршрута и клиентский провайдер могут входить в артефакты сборки. Кандидаты на проверку памяти — рост V8 heap после прогрева, внешняя память Argon2 и удержание GPU-ресурсов после ухода с `/atlas`. Глобус вызывает `dispose()` для принадлежащих ему текстур при размонтировании и при позднем завершении загрузки. Для проверки утечки GPU нужен отдельный браузерный тест с повторными переходами. 30-минутный HTTP-тест сопоставляет ранние и поздние образцы серверного процесса отдельно от прогрева.

## Среда и измерения

Windows 10.0.26200, Ryzen 7 7735HS, 16 логических CPU, 15,24 ГиБ видимой RAM, Node.js 24.22.1. Проверка `wsl -l -v` вне песочницы показала единственный дистрибутив `docker-desktop`, Ubuntu отсутствует. Замеры идут через loopback на одном хосте с генератором, без Nginx/TLS и без лимитов Ubuntu. `% ядра` — процессорное время Node за интервал, где 100% соответствует одному логическому CPU. CPU хоста учитывает и фоновые процессы. RSS семплируется раз в секунду, краткие пики возможны между образцами. `p95 event loop` вычисляется внутри каждого окна семплирования.

Production build завершился за **12,02 с**, а первый `next start` сообщил `Ready in 609ms`. По 22 процессам сборки максимальная наблюдаемая сумма последних RSS работающих PID — **1575,32 МиБ**. Отдельный процесс достиг 496,61 МиБ RSS, 311,73 МиБ heapUsed, 428,50 МиБ heapTotal, 10,57 МиБ external. CPU хоста в выборке в среднем 40,95%, максимум 100%. Среднее взвешено образцами процессов с перекрывающимися интервалами. Сумма RSS может повторно учитывать общие страницы и пропускать пики между отсчётами. Для ВМ с 4 ГиБ рекомендована сборка на Linux CI или отдельной Linux-машине. Проверка локальной сборки на 4 ГиБ вместе с действующим рантаймом и Nginx ещё нужна.

Повторный production build после серии прошёл за **10,81 с** с наблюдаемым пиком суммы RSS **1692,46 МиБ**. На Windows оба замера укладываются в диапазон 1,54–1,65 ГиБ по этой методике.

Максимальная проверенная ступень смешанного сценария — **200 VU на Windows**, 60,71 RPS с учётом 1051 ответа 429. Это 200 скриптовых пользователей с паузами. Перезапуски тестовых процессов во время измеренных окон не наблюдались. Отдельного источника счётчика OOM на Windows нет. Скрипт собирает `memory.events` на Linux с cgroup v2.

## Воспроизведение на Ubuntu

Запускать из отдельного тестового checkout с Node 24, без production `.env`, учётных данных и SMTP. Нагрузочный генератор принимает manifest loopback-стенда, fixtures и отдельный путь результата. Рабочие каталоги должны быть пустыми. Сессии, пароли и ссылки активации из них не коммитить.

```bash
npm ci
node scripts/performance/run.mjs build .perf-build
node scripts/performance/metrics.mjs .perf-build
systemd-run --user --scope -p CPUQuota=200% -p MemoryMax=4G -p MemorySwapMax=2G \
  node scripts/performance/run.mjs start .perf-2cpu-4g 3469
```

Во втором терминале выполнить следующие команды.

```bash
node scripts/performance/seed.mjs --server .perf-2cpu-4g/server.json \
  --output .perf-2cpu-4g/fixtures.json --count 200
node scripts/performance/suite.mjs .perf-2cpu-4g/server.json .perf-2cpu-4g/fixtures.json
node scripts/performance/metrics.mjs .perf-2cpu-4g
```

Для профилей 2/2 и 4/8 указать соответственно `CPUQuota=200%`, `MemoryMax=2G` и `CPUQuota=400%`, `MemoryMax=8G`, каждый раз использовать новый каталог. Процесс нагрузки держать вне scope. На отдельной машине генератор можно подключить через локальный SSH-туннель на стенд с тем же loopback-портом. Для сценария регистрации нужен общий доступ к тестовому outbox. Локальная копия манифеста должна указывать абсолютные пути в каталоге манифеста запуска. Прямой замер на собственной тестовой Ubuntu-ВМ точнее по характеристикам CPU и диска. Для измерения вкладов Nginx/TLS использовать отдельный staging-контур.

Генератор выдерживает 3–8 секунд между действиями смешанного профиля. Пропорции 25/20/25/15/10/5 относятся к действиям, каждое действие может отправить несколько запросов. HTTP-сценарий проверяет идентификатор аккаунта, содержимое HTML/JSON, запись и чтение позиции урока и активацию через локальное письмо. Сетевые окна лимитов сохраняются между ступенями. Если все запросы операции отклонены, пропускную способность успешных операций по этой ступени оценить нельзя.

Для отдельных сценариев запустить свежий стенд на другом порту вне окна смешанного теста. Можно применить тот же systemd scope. Переменная `SOPHIA_PERF_SAMPLE_MS=150` полезна для измерения коротких браузерных действий. На HTTP-сериях рекомендуется секундная выборка по умолчанию.

```bash
node scripts/performance/run.mjs start .perf-focused 3470
# В другом терминале
node scripts/performance/seed.mjs --server .perf-focused/server.json \
  --output .perf-focused/fixtures.json --count 200
node scripts/performance/load.mjs --server .perf-focused/server.json \
  --fixtures .perf-focused/fixtures.json --output .perf-focused/login-25-120.json \
  --mode login --users 25 --seconds 120
node scripts/performance/load.mjs --server .perf-focused/server.json \
  --fixtures .perf-focused/fixtures.json --output .perf-focused/write-50-120.json \
  --mode write --users 50 --seconds 120
node scripts/performance/metrics.mjs .perf-focused
npx playwright install chromium
node scripts/performance/browser.mjs .perf-focused/server.json \
  .perf-focused/fixtures.json .perf-focused/browser-interactions.json
curl -sS -o /dev/null -w '%{http_code}\n' -H 'Origin: http://127.0.0.1:3470' \
  -H 'Content-Type: application/json' --data '{}' http://127.0.0.1:3470/api/philosopher-chat
node --input-type=module -e "import {DatabaseSync} from 'node:sqlite'; const db = new DatabaseSync(process.argv[1], {readOnly:true}); console.log(db.prepare('PRAGMA quick_check').all()); db.close()" .perf-focused/accounts.sqlite
```
