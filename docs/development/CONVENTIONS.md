# Соглашения разработки

Эти правила применяются к коду Phase 1. ESLint настроен в `eslint.config.mjs`; отдельного форматтера нет. Размещение модулей — в [STRUCTURE.md](../architecture/STRUCTURE.md), обязательные ограничения — в [INVARIANTS.md](../architecture/INVARIANTS.md).

## Именование

- Файлы компонентов и обычных модулей: `kebab-case`, например `demo-question.tsx`, `evaluate-answer.ts`.
- React-компоненты и типы: `PascalCase`, например `DemoQuestion`, `QuestionOption`.
- Функции, переменные и hooks: `camelCase`; hooks начинаются с `use`, логические значения — с понятных `is`, `has`, `can`.
- Имена констант уровня модуля, представляющих фиксированные значения: `UPPER_SNAKE_CASE`.
- Служебные имена Next.js (`page.tsx`, `layout.tsx` и другие) следуют соглашениям фреймворка.
- Имена отражают предметную роль, а не техническую неопределённость вроде `data2` или `helperNew`.

## Импорты и типы

Группировать импорты: внешние зависимости, внутренние модули, относительные импорты, стили. Импорты только типов обозначать `import type`. Не применять alias, пока он не настроен в проекте. Удалять неиспользуемые импорты; не вводить циклические зависимости.

Типы располагать рядом с владельцем контракта; общие типы выделять при нескольких реальных потребителях. Внешние данные считать непроверенными до валидации. Не подменять проверку данных утверждением типа.

## React

- Использовать функциональные компоненты и явно описанные props.
- Компонент отвечает за одну понятную часть UI; выделять дочерний при самостоятельном поведении или повторном использовании.
- Держать локальное состояние рядом с взаимодействием; вычисляемые значения получать из исходного состояния, не дублировать их без причины.
- Выносить предметные правила в проверяемые функции, учебный контент — в отдельные типизированные данные.
- Добавлять `use client` только там, где нужны клиентские возможности. Серверные модули не должны попадать в клиентский граф импортов.
- Не применять эффекты для вычислений, которые можно выполнить при рендере. Для списков использовать устойчивые ключи предметных объектов.

Документы писать в UTF-8. Существенные изменения отражать в профильном документе, а статус — в [CURRENT_STATE.md](CURRENT_STATE.md).
